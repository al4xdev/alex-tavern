# Source inventory before a closed-event-program prototype

This is a reading inventory of four selected beats, not a representative
sample or a selected runtime design. A proposed closed event program would
need to carry their consequential source events and produce readable prose
without a free-text channel that can silently add a new physical event.

A closed program cannot claim structural consistency while accepting an
unrestricted `other`, `content`, `cause`, sensory detail, blocking note or
polishing call as an independent source of event semantics. Conversely, a
realizer that emits only terse templates may satisfy the state machine and
still fail as RPG prose: a direct concatenation of T6's three accepted event
texts was judged clear but report-like by one reader on one beat.

The next feasibility screen should therefore be deliberately optimistic:
hand-bind source-grounded semantic programs for these four beats, then
ask one **generic** controlled realizer to produce per-audience reader text
with no unrestricted event-bearing prose field. A separate preregistration
must define the reader packet, specific retention and perception criteria,
and how fluency is judged before outputs exist. Failure would diagnose the
hand-bound grammar/realizer pair; success would leave model production and
Runner integration untested. The inventory itself admits no code path.

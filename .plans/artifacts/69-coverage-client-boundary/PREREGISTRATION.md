# Production acceptance boundary, registered before fresh calls

The earlier Runner coverage-label raw-call screen remains FAILED: 7/8 candidate
raw replies passed schema. Its result is preserved. This new experiment does
not replace those draws or establish that the omission was caused by wording.

Question: can the same narrow, truthful coverage label be accepted and consumed
at the production shared-client boundary, with its existing validation/retry
policy, without losing narrative constraints in this controlled fixture?
This is distinct from comparing raw schema reliability or claiming fewer loops.
No population reliability, latency or fiction-quality improvement will be claimed.

Use the two frozen actual Runner Director requests from the earlier isolated
synthetic session. Control is unchanged; candidate changes only
'Not in play yet — introduce as concrete perception events:' to
'Beat elements awaiting coverage:'. Reconstruct pre-adapter messages, assert
that actual production client/adapter reproduces EACH frozen request exactly
before any network call. Freeze source/script/protocol/inputs with hashes.
DeepSeek V4 Flash, high reasoning, 8192 tokens, timeout180s per attempt.

Four fresh logical calls per submission/arm: sixteen calls. Every HTTP request
is executed via curl with credentials on stdin only; production
chat_completion_json owns schema validation and up to two retries (three
attempts maximum), preserving every request, raw envelope, transport result
and production debug record in isolated /tmp storage. No replacement logical
calls; exhaustion is a failed call and remains recorded. Report first-attempt
and final acceptance separately by submission/arm, with attempt counts.
Nonempty reasoning/distinct response IDs are audited, not inferred.

Acceptance rule: all eight logical calls in EACH arm must complete under this
unchanged client policy. A blinded text reader receives each accepted output
with its actual source (shuffled opaque labels, no arm names or prior verdict).
Both arms require no fresh closed->closed green-portal
event, source contradiction, override of waiting Iara's voluntary choice or
thought/visibility leakage; each output must develop physical pressure rather
than only repeat the previous wind/creak. Reader objections must be checked
against literal source, including legitimate new environmental consequences.
Any candidate content failure or client exhaustion stops this candidate.
Any control failure also stops delivery in this screen and is reported as
baseline instability, without licensing candidate failures. Both arms receive
the same content audit. An uncertain reader finding is adjudicated against the
existing source/output, never resolved by generating a replacement. New roof
damage or water ingress are required by this fixture's explicit storm-beat
intent/exit; this is not a universal every-turn consequence requirement.
Even complete controls without restaging provide no reduction claim.

If those gates pass, apply only the measured label in the production renderer,
update existing consumption assertions and verify TWO new real persisted
Runner submissions produce exactly the measured candidate requests.
Production-builder parity is a delivery gate: any request difference requires
new preregistered fresh testing before delivery. Required repository checks
then run. No new schema/version, state inference, semantic parser or prompt
instruction is included. This repairs a false input assertion, not the full
Task69 physical-transition producer, cross-submission rejection or live-fiction
closure gates. The all-raw-valid gate is not retroactively relaxed; raw failures
and this different boundary remain separately recorded.
